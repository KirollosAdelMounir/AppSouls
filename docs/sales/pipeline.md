# Sales pipeline

The `/sales` workspace implements the first part of the approved pre-order CRM flow: leads, opportunities and lead conversion. It is available to active Owner/Admin memberships. Technical and Customer roles cannot read or mutate commercial pipeline data. Authorization rechecks the tenant, membership role, active organization and session security stamp on every service operation.

Leads capture contact/company, email, phone, source, notes, owner and optional follow-up. Owners must be active Owner/Admin members of the same organization. Opportunity records link an authorized customer to an owner, title, expected value, currency and follow-up. Supported currencies are USD, EUR, GBP, EGP, SAR and AED; amounts are nonnegative with at most two decimal places, without currency conversion or mixed-currency totals. Follow-up entry is explicitly UTC and is normalized to microsecond precision before persistence and request hashing for PostgreSQL/SQL Server compatibility.

Lead stages are New → Qualified, with disqualification from New/Qualified and reopening Disqualified → New. Disqualification/reopening requires a reason. Conversion is a separate command available only for Qualified leads. It creates a new customer, a Qualified opportunity and both history events in the same database transaction while marking the lead Converted. The UI states that conversion creates a new company; it does not silently merge companies by email. An idempotent request retries the exact conversion rather than creating another customer. Concurrent conversions are protected by optimistic versions and uniqueness constraints.

Opportunity progression is New → Qualified → Proposal → Negotiation → Won. An open opportunity may become Lost with a reason; Lost → Qualified also requires a reason. Won is terminal. A sales stage is not a purchase authorization: marking Won does not create an order, contract, entitlement or license.

Create/stage/convert commands carry an operation ID. Retries require the same normalized payload and actor; reusing an operation ID with changed details conflicts. Stage updates also carry the expected record version. History records the actor and UTC time, is append-only through the application context, and is protected by tenant-composite foreign keys. This is application-enforced history, not a claim of database-administrator-proof auditing.

The screen owns state in `SalesPipelineViewModel`, with focused lead/opportunity/stage components. Lists use stable ordering, server pagination (20 per page in the UI; maximum 50 through the API) and a latest-50-event history view. Current customer and owner selectors are bounded to 100; searchable selectors and full profile editing remain separate work. Selectors/calendar use shared controls; inline editors restore focus on cancel and successful saves focus the record heading. The shared CSS motion system respects reduced-motion preferences.

Attribute-routed controller endpoints live under `/api/sales`. Cookie-authenticated mutations require antiforgery verification and are rate limited. Scalar describes the API contracts. PostgreSQL and SQL Server have separate SalesPipeline migrations. PostgreSQL integration tests cover tenant access, foreign relationships, idempotency, stage transitions, amounts, concurrent conversion, rollback and paging. SQL Server model/script generation is checked; live SQL Server remains an acceptance requirement.

Versioned quotations, quote acceptance into order snapshots, pre-order fulfillment, amendments and detailed customer contacts remain unimplemented. They must preserve offered terms and commercial release conditions before granting production software access.
